---
title: CIP-113 programmable tokens
description: How programmable tokens are served, and why they need CIP-26 or CIP-68 metadata too.
---

[CIP-113](https://github.com/cardano-foundation/CIPs/pull/444) defines **programmable tokens**: tokens whose transfers
and minting are governed by on-chain scripts, for example for regulated stablecoins or tokenised securities. A token is
registered in an on-chain **registry**, a sorted linked list of nodes, one per policy.

## What the registry serves

A registry node says only that a policy is programmable, and which scripts govern it. It has **no name, ticker or
logo**. So a programmable token is served only with its ordinary metadata, from [CIP-26](../cip26/) or
[CIP-68](../cip68/), and the V2 response adds:

```json
{
  "type": "PROGRAMMABLE",
  "extensions": {
    "cip113": {
      "minting_logic_script": "…",
      "transfer_logic_script": "…",
      "third_party_transfer_logic_script": "…",
      "unfracking_logic_script": null,
      "global_state_policy_id": "…"
    }
  }
}
```

A registered policy whose tokens have no CIP-26 or CIP-68 metadata **is not served**: there would be nothing to show.
Give your programmable token metadata the same way as any other token.

## Checking a registry node

The [validator](../../validator/), CIP-113 tab, reads a registry node datum the way the registry does and shows the
extension it would serve, or why it cannot read it. It is a simplified check. To build and submit a registration, use
the CIP-113 tooling in [cip113-programmable-tokens](https://github.com/cardano-foundation/cip113-programmable-tokens).
